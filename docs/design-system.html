Mulia Code Design System

A single visual and interaction language for web, mobile, and command-line software — dense, technical, quiet. Dark-first, light-equal, WCAG 2.2 AA throughout. Every value here is a token; consume tokens, never literals.

01

02

Principles

Six rules that settle arguments. Any choice a token doesn't cover, one of these does.

Density over decoration

Chrome competes with content. Start tighter than feels comfortable, and add space back only where it improves comprehension. Skip the shadow wherever a 1px border does the job.

One accent, used for meaning

Colour signals action or state, nothing else. The interface stays warm neutral, with one sea-green for "you can act here" and four status hues on top. Nothing gets coloured just to look nice.

Text is the primary material

Hierarchy comes from size and weight, not colour or boxes. Monospace flags anything machine-generated — identifiers, paths, counts, hashes, durations.

Fast by default

Micro-interactions run in 120ms, panels in 220ms. Reach for optimistic updates and skeletons over spinners whenever the shape of the result is already known.

Accessible is not a variant

Contrast, focus, target size, and reduced motion are built into the tokens themselves. A component that fails one of them is broken — not an alternate, lighter version.

One system, three surfaces

Web, mobile, and CLI all adapt the same tokens. Someone moving from terminal to app should recognise the same software — not just a family resemblance.
03

Colour

WCAG 2.2 AA verified

Three layers: primitives (raw ramps) → semantic tokens (meaning) → component tokens. Product code only ever reads semantic tokens, so a new theme touches a single file.

Neutral ramp

Eleven steps, warm-cast. This does the most work of anything here and gets noticed the least: almost every technical interface defaults to a cool blue-grey, so warming the ramp toward undyed cloth changes how the product feels before a single accent colour shows up — at no cost, since the ramp still clears every contrast target.

Primary — toska

It splits into --accent-solid (fills), --accent-text (links and text), and --accent-on-solid (a label sitting on a fill). No single hue clears 4.5:1 both as a fill background and as body text, so the system settles the accessible pairing itself instead of leaving it to whoever implements it.

Secondary — kencana

Kencana carries the identity, not the interface. Keeping it out of the interactive layer is exactly what keeps a two-colour brand from turning into an ambiguous one.

Status

Four hues, each with a solid, a text-safe variant, and a low-chroma tint. Every one sits more than 40° from toska on the wheel, because a primary action must never be mistaken for a status at badge size. Warning shifted from amber to orange specifically to put clear distance between it and kencana.

Do

Pair every status colour with an icon or a word. Roughly 8% of men have some colour vision deficiency, and CI logs strip colour out entirely.

Don't

Rely on a red or green row background as the only signal that something failed. That's a 1.4.1 failure, and it disappears entirely in monochrome print.

Typography

Two typefaces. Inter for interface and prose, JetBrains Mono for anything a machine produced. The split is the information design — if it's set in mono, it's data you can copy, grep, or paste into a terminal.

Borders separate, shadows float. Anything that sits in the page flow gets a border. Shadow is reserved for what overlays content — menus, modals, the command palette.

07

Motion

Motion exists to clarify where something came from — never to entertain, and never to make the user wait.

TokenDurationEasingApplies to
--d-micro120msease-outHover, focus, toggle, checkbox
--d-panel220msease-out / ease-inModal, drawer, popover, toast

Entrances ease out, exits ease in. Nothing animates inside a data table — a row that slides while you're reading it makes you lose your place. Flash a changed row's background for 400ms instead, and never more than three times per second.

Reduced motion is a hard requirement

Every transition collapses to 1ms under prefers-reduced-motion: reduce. Vestibular disorders make large-movement animation genuinely painful.

08

Iconography

One family, one weight: a 16px grid, 1.75px stroke, round caps and joins, no fills — all drawn on the same optical grid so they hold their density beside 13–14px text.

16 × 16 gridstroke 1.75currentColorsizes 16 / 20 / 24
Do

Give every standalone icon button an aria-label, and mark purely decorative icons aria-hidden="true" so nothing gets announced twice.

Don't

Ship an icon-only control for a destructive or ambiguous action. Delete, publish, and merge get words — an unlabelled trash can is a support ticket waiting to happen.

Treat this set as a working sample. Extend it on the same grid, or adopt a libre set that already matches — Lucide runs 16/24px at a 2px stroke and rescales cleanly to 1.75.

09

Component API

naming

One taxonomy for every component: four axes, always the same order, always the same vocabulary. Learn one component's props and you can guess the next one's.

AxisValuesApplies to
sizesm · md · lgAnything with a height. md is always the default.
toneneutral · primary · brand · success · warning · danger · infoOnly where colour carries meaning.
variantsolid · outline · ghostAnything with a fill decision.
statedefault · hover · active · focus · disabled · loadingRendered, never passed. Every component implements all six.
 
// Same axes everywhere. No component invents its own words.
<Button size="md" tone="primary" variant="solid">Install</Button>
<Badge  size="sm" tone="success" variant="ghost">Ready</Badge>
<Alert  tone="danger" variant="outline" />
size → tone → variantmd is defaultstate is never a prop
Do

Reuse the axis names even when a component only supports two values. A tone that accepts nothing but neutral and danger is still called tone.

Don't

Introduce color, kind, type, appearance, or intent as synonyms. Five names for one concept is how a library stops being learnable.

Keep tone to components where colour genuinely carries meaning — buttons, badges, alerts, progress, status dots. A tinted avatar communicates nothing and still costs a contrast audit.

10

Buttons

One primary button per view, exactly. If two things look equally important, neither one is.

Variants

Read the docs
primarysecondaryghostdangerdanger-ghostlink

Primary is the reason the view exists. Secondary is the way out. Ghost handles repeated, low-weight actions in toolbars and rows. Danger is reserved for irreversible destruction, and it never sits directly beside the primary action.

Sizes and states

sm: rows, toolbarsmd: defaultlg: mobile, empty statespress Save to see the loading state

A loading button keeps its width and sets aria-busy — it never collapses to a bare spinner, since layout that shifts under the cursor causes mis-clicks. Disable as little as possible: an always-enabled submit that explains what's missing beats a dead button that explains nothing.

Icon, group, split

icon buttontoggle groupsegmented controlsplit button

Icon buttons render at 28–32px but carry a 44px hit area via a transparent pseudo-element, meeting target size without inflating visual density.

Form controls

Labels stay visible, always above the field. Placeholder text is never a substitute — it vanishes on focus, fails contrast, and is invisible to anyone reviewing an already-filled form.

Lowercase letters, numbers, and hyphens. Used in URLs.

Do

Tie help and error text to the field with aria-describedby, mark invalid fields aria-invalid, and say what to do next, not just what went wrong.

Don't

Validate on every keystroke while someone is still typing. Validate on blur instead, and only re-validate live once a field has already failed.

    Tables

    The densest surface in the system, and the one most often broken. Use real <table> markup with <th scope> — a grid of divs is unusable with a screen reader, which depends on header association to announce what each cell actually means.

    Recent deployments · 4 of 128
    Status Commit
    acme-api Ready8f2c91b 1m 42s2,410,882
    acme-web Buildingc14ee02 —918,304
    acme-worker Failed3a90d7f 0m 18s0

    Numeric columns right-align with tabular figures; identifiers stay monospaced but left-aligned. The header row is sticky, and scroll-padding-top stops a focused row from hiding beneath it — the classic 2.4.11 failure. Long paths truncate from the middle, since the ends are where the meaning lives. Sorting sets aria-sort so the state gets announced, and the selection count lives in a live region.

    Past roughly 200 rows, paginate or virtualise. Virtualised rows have to keep aria-rowcount and aria-rowindex accurate, or a screen reader ends up reporting the wrong total and position.

    Feedback

    Three channels, chosen by how long the message needs to stick around. Inline for a specific field. Alert for the current page. Toast for the result of an action you just took.

    Region migration scheduled

    eu-west-1 is moving to new hardware on 12 March, 02:00 CET. No action needed on your end.

    Domain verified

    acme.com now routes to this project.

    Approaching build minute limit

    You've used 92% of this month's allowance. Builds pause once you hit 100%.

    Build failed: missing environment variable

    DATABASE_URL isn't set for production. Add it in Settings → Environment, then redeploy.

    role=note / status / alerticon + colour + text, never colour alone

    Reserve role="alert" for what genuinely needs to interrupt — it forces a screen reader to break off mid-sentence. Informational and success messages use role="status" instead, which waits for a natural pause.

    Toasts

    bottom-rightsuccess auto-dismisses at 5sanything actionable persists

    Anything with an action inside it must not auto-dismiss — a timed message is a 2.2.1 failure for anyone reading slowly or using a magnifier. Errors stay put until someone dismisses them. Never let a toast be the only place important information lives.

    Rules

    Never rely on ANSI colour alone — every state carries a symbol and a word too, since colour gets stripped in CI logs and is unavailable to a large share of users. Pull from the terminal's semantic palette rather than hardcoded hex, so a user's own theme keeps working. Detect a non-TTY stdout and drop colour, spinners, and box drawing automatically; honour NO_COLOR, and offer --json for machine consumption. Indent nesting by two spaces, right-align only numbers, and truncate long paths from the middle. Use a spinner under five seconds, a progress bar with an ETA above it, and plain sequential lines when piped. Errors state what happened, why, and the fix, in that order, one-line summary first, with a stable error code mapped to a documentation page. Destructive commands confirm interactively and accept --force for scripts. Every command answers --help in the same shape: Usage → Description → Flags → Examples.

    Accessibility

    WCAG 2.2 AA

    The system targets WCAG 2.2 level AA. EN 301 549, the harmonised European standard, formally sits at v3.2.1 and still cites WCAG 2.1 — but v4.1.1, which adopts 2.2 AA, went to public review in late 2025 and is expected in the Official Journal around late 2026. The six new criteria are cheap to build in now and expensive to retrofit later, so 2.2 is the floor here, not the ceiling.

    The six criteria new in 2.2

    CriterionLevelHow this system meets it
    2.4.11 Focus Not ObscuredAASticky headers use scroll-padding-top; overlays never cover the focused element.
    2.5.7 Dragging MovementsAAUpload has Browse, kanban cards have Move to…, resize handles take arrow keys, sliders take arrow keys.
    2.5.8 Target SizeAA24×24px minimum, 44×44px on touch. Icon buttons render at 32px with a transparent 44px hit area.
    3.2.6 Consistent HelpAHelp is the last sidebar item on every screen, and --help answers on every command.
    3.3.7 Redundant EntryAWizards show earlier answers rather than asking again; "same as billing" is auto-filled, not re-keyed.
    3.3.8 Accessible AuthenticationAANo cognitive function test. Password managers and passkeys work, paste is never blocked, OTP accepts one pasted string.

    The three that break real products

    Blocking paste in a password or 2FA field is a straight AA failure, and it defeats password managers — the opposite of what a security control should do. Puzzle CAPTCHAs fail 3.3.8; use a device or token-based check instead. A sticky header covering a focused row fails 2.4.11 on nearly every dense table ever built. Test all three by tabbing through them, not by reading the spec.

    Beyond the checklist

    Conformance is the floor, not the finish line. Ship every new pattern with a real keyboard-only pass and a screen reader pass — NVDA on Windows, VoiceOver on macOS and iOS, TalkBack on Android. Automated tooling only catches roughly a third of real issues. Publish an accessibility statement: public sector bodies must under Directive 2016/2102, and the European Accessibility Act expects accessibility information inside product documentation. Name the known gaps and give people a way to report problems — in an open-source project, that's just a labelled issue template, which costs nothing and is more honest than a badge. For the CLI, EN 301 549 chapter 11 covers non-web software: don't defeat platform accessibility features, keep terminal output legible when read linearly, and never let colour be the only carrier of meaning.

    Scope check

    The European Accessibility Act covers specific product and service categories, with microenterprise exemptions and national implementations that vary. Treat this checklist as engineering practice, and confirm your actual legal obligations for your sector and member state with someone qualified to advise on it.

    Voice & content

    Words are design material too. Sentence case everywhere, plain verbs, no exclamation marks, no apologies.

    Write

    "Save changes" · "Delete project" · "Connect a repository"

    A control names exactly what will happen, and the same verb resurfaces in the result: Publish → Published.

    Not

    "Submit" · "OK" · "Are you sure?"

    Generic verbs leave the user guessing. A confirmation that doesn't name the consequence is just a coin flip.

    Write

    "DATABASE_URL isn't set for staging. Add it in Settings → Environment, then redeploy."

    Not

    "Oops! Something went wrong 😅 Please try again later."

    Errors don't apologise, and they're never vague. Log the stack trace; show the fix.

    Name things the way the user thinks about them, not the way the system happens to be built: people manage notifications, not webhook configuration. Keep the vocabulary identical across interface, CLI, and documentation — one object, one name. No marketing language inside the product; nothing here is blazing fast or seamless.

    Data visualisation

    categorical · sequential · diverging

    Charts are where most design systems give up and let each team improvise. The hard part was never drawing a bar — it's a categorical ramp that stays distinguishable across both themes and under the common colour vision deficiencies. That ramp gets defined once, here.

    Categorical ramp

    8 series maximumordered by distinctnessslot 8 is neutral, for "other"

    Order matters more than the set itself. Most charts show two to four series, so the first four are maximally separated: teal, gold, blue, red. That sequence deliberately keeps red away from green, the single most common way a chart becomes unreadable. Every colour clears 3:1 against its own theme background, which is what WCAG 1.4.11 requires of graphical objects the content depends on.

    Simulated colour vision deficiency

    deuteranopia ≈ 6% of menprotanopia ≈ 2%tritanopia < 0.01%

    These rows are approximations, not a substitute for real testing — but they show the property that matters: adjacent swatches stay distinguishable because the ramp varies lightness as well as hue. A ramp that varies hue alone collapses into two or three indistinguishable bands under deuteranopia.

    Sequential & diverging

    0sequential · one quantitymax
    −100%diverging · signed change+100%

    The diverging ramp runs red to teal, never red to green. A red-green diverging scale is the most common accessibility failure in dashboards: to someone with deuteranopia both ends look the same, so a chart of gains and losses collapses into noise. Red-teal and orange-blue both hold up.

    Rules

    RuleWhy
    Label series directly, not in a legendA legend forces the eye to travel and to hold a colour in memory. Direct labels remove both costs, and survive colour blindness entirely.
    Vary line style as well as colourSolid, dashed, dotted gives a second channel at zero cost. Scatter plots use distinct marker shapes for the same reason.
    Every chart has a text summaryOne sentence stating the trend and the notable value. This is the accessible name for screen reader users and doubles as the thing most readers actually want.
    Every chart has a table viewThe underlying numbers must be reachable. A toggle costs little and satisfies 1.1.1 properly.
    Bar charts start at zeroA truncated bar axis misrepresents magnitude. Line charts may truncate, with the axis clearly labelled.
    Maximum eight seriesBeyond eight, no palette stays distinguishable. Group the tail into "other" and offer drill-down.
    No pie chart beyond three slicesAngle is the hardest visual encoding to compare. Use a stacked bar, which reads left to right and labels cleanly.
    No dual y-axisTwo scales on one plot make any correlation look intentional. Use two stacked charts sharing an x-axis.
    Data points are focusableKeyboard users need to reach values. Arrow keys move along a series; the focused point announces its label and value.
    Respect reduced motionEntry animations on charts are decorative. Under prefers-reduced-motion they do not run.

    A tooltip on hover is a convenience, never the only route to a value — it's unreachable by touch and by keyboard alike. Whatever a tooltip says has to also live in the table view or on the axis.

    Data grid

    virtualised

    Past roughly 200 rows, a table stops being a table. This grid renders only the visible window across 10,000 rows, keeps the first column frozen, and moves cell focus with the arrow keys.

    10,000 rows Arrow keys move · Enter edits · Space selects
    Row 1 of 10,000 rendering 0 nodes

    What virtualisation must not break

    RequirementImplementation
    Total size is announcedaria-rowcount on the grid reports 10,000, not the 14 rows in the DOM. Without it a screen reader announces the window size and the user believes the data is tiny.
    Position is announcedEvery rendered row carries its true aria-rowindex, and every cell its aria-colindex.
    One tab stopThe grid is a single stop. Arrow keys move the focused cell, Home and End jump to row ends, PageUp and PageDown move a screen, ⌘↑ and ⌘↓ reach the first and last row.
    Focus survives scrollingMoving focus scrolls the window to keep the cell visible, and never lets the sticky header cover it.
    Editing is explicitEnter enters edit mode, Enter commits, Esc reverts. Focus returns to the cell either way.
    Selection is separate from focusSpace toggles selection on the focused row. Moving focus does not change selection — conflating the two makes multi-select impossible by keyboard.
    Frozen columns stay reachableThe frozen column is in normal DOM order, so linear reading and arrow navigation are unaffected by its visual pinning.

    Row height is fixed at 34px, which is exactly what makes the maths trivial: start = floor(scrollTop / 34). Variable heights need a measured offset cache, and they're worth avoiding unless the content genuinely demands them. When filtering removes rows, aria-rowcount updates to the filtered total — reporting the unfiltered count is a small lie, but a real one.

    Choose the plain table when you can

    Virtualisation costs correct ARIA bookkeeping, breaks the browser's find-in-page, and complicates printing and copy-paste. Under a few hundred rows, a real <table> with pagination is faster to build, more accessible by default, and better behaved overall. Reach for this grid only when the data genuinely won't fit.

    31

    Governance

    A design system starts decaying the moment it stops being the path of least resistance.

    Consume tokens, not values

    Every project imports tokens.css or tokens.json. A raw hex or an off-grid pixel value in a stylesheet is a defect — write a lint rule to catch it.

    Extend here first

    If a screen needs something this document doesn't cover, add it here first, then build. One-off decisions made inside a feature branch are how systems die.

    Version deliberately

    Semantic versioning governs the token package. Renaming or removing a token is a major bump; adding one is minor. A token's meaning never changes silently.

    Review after real use

    Revisit this after two or three shipped projects. The accent hue, the 14px base, and the radius scale are the values most likely to need a second look once seen at full page scale.

    Next decisions. A density toggle applied globally rather than per table. Localisation — German and Finnish run 30–40% longer than English, Indonesian runs shorter, so every fixed-width control needs testing against all three before translation. And how to distribute it: a single @muliacode/tokens package, or tokens plus a headless component layer that supplies keyboard behaviour for combobox, menubar, and date picker without rewriting it once per framework.
